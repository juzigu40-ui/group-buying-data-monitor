# 零技术门店KPI监管接入清单

## 先说结论

- 这次客户要的重点不是泛舆情监控，而是门店内容发布 KPI 监管。
- 老板真正要看的，是每个门店当天引导用户发了多少条内容、有没有达到要求。
- 最推荐的交付方式不是让门店自己搭环境，而是先按“托管代跑 + 飞书推送”跑通。

## 客户最少需要准备什么

1. 一个飞书群，用来接收系统结果。
2. 飞书群机器人 webhook。
3. 门店清单。
4. 每个门店的每日目标值。
5. 如果继续沿用 OpenClaw，需要把碰一碰 / 内容库导出的内容写进标准输入文件。

## 这套系统怎么把内容分到具体门店

1. 如果内容来自门店碰一碰、内容库或活动台账，OpenClaw 导出时要带 `source_store_id` 和 `source_store_name`。
2. 系统收到这两个字段后，会把内容直接记到对应门店，不再只靠品牌词模糊搜索。
3. 每个门店可以单独设置 `daily_target_count`，系统会自动算当天是否达标、还差几条。
4. 如果没有门店来源字段，系统仍然能做公开内容精筛，但这更适合辅助监控，不适合做严格 KPI 考核。

## 老板在飞书里主要看什么

1. 今日相关内容。
2. 门店直连记账。
3. 今日门店 KPI 达标情况。
4. 哪些门店还差几条。

## 什么时候需要重新登录平台

- 不需要重新登录：
  - 改规则。
  - 改飞书推送。
  - 改看板口径。
  - 改每日目标值。
- 需要重新登录：
  - 要补抓新的真实平台数据。
  - 平台登录态过期。
  - 平台页面字段变了，需要重新核对采集链路。

## 最推荐的交付方式

1. 第一步：我们先托管代跑，把结果稳定推到飞书。
2. 第二步：老板只在飞书里看门店 KPI 结果和交付页，不直接碰脚本。
3. 第三步：如果后面确实要自己跑，再补完整技术运行包和自跑指导。

## 如果客户后面要自己跑

最低要求：

1. 仓库代码。
2. 对应门店的 profile 目录。
3. Python 环境。
4. 飞书 webhook。
5. 至少有一位能执行终端命令的人。

如果没有这 5 样，不建议直接切客户自跑。
